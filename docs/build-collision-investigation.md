# 建造碰撞排查方案

## 已确认的事实

- 当前游戏版本为 `0.10.35.29088`。独立测试档中，矿机请求的位置为 `(124.764579, -19.824285, 155.308846)`，旋转为 `0`，目标矿脉为 `1`。
- 更新到本次源码构建后，`task:3` 仍返回 `collision / Collide`，没有创建矿机。此前 `task:2` 清理了附近 10 个植被对象，不能据此解释或解决碰撞；停止把清理植被作为建造前置条件。
- 原生 `Collide` 不只来自一种检查。`BuildTool_Click.CheckBuildConditions()` 包含建筑碰撞盒重叠、矿机额外的 layer 11 检查、出生飞行仓距离检查等路径。仅凭错误名称不能确定命中对象。
- 原生流程顺序为 `DeterminePreviews → UpdateCollidersForCursor → UpdatePreviewModels → CheckBuildConditions`。Mod 手工创建预览后直接校验，矿机还跳过了 `ActivateBuildColliders`。
- `NearColliderLogic.UpdateCursorNear()` 读取 `actionBuild.activeTool.buildPreviews`，并受 `actionBuild.active` 控制。临时创建的自动化工具没有被设为当前工具，因此简单补调此方法不能保证检查的是本次请求。
- `ActiveCollidersInArea()` 会过滤 `notForBuild`，与原生光标附近更新的筛选条件不同，不能当作等价替代。
- 原生重叠检查会根据 `BuildPreviewModel.index` 和 `preview.previewIndex` 排除自身预览。Mod 没有运行对应的预览模型同步；残留 UI 预览干扰是待验证假设，尚不是已确认根因。
- Mod 会修改共享的 `controller.cmd`，但当前方法的 `finally` 只释放临时工具，没有恢复本次改动的命令字段。这使 UI 状态是否影响校验成为必须验证的条件。

## 实施顺序

1. 保留当前失败请求、存档和 DLL 哈希，暂停布局变更。对原生校验添加仅用于诊断的日志，记录返回 `Collide` 的具体分支、预览索引与世界姿态、碰撞盒、命中 collider 的 layer、对象类型和 ID；不能把另一次独立重叠查询当成原生失败分支的确定证据。
2. 用同一位置和朝向比较原生建造预览与 API 校验。分别记录退出建造模式和存在 UI 预览时的结果，确认是否受到共享命令、活动工具或预览模型影响。预览比较不点击确认建造。
3. 根据命中证据修正自动化工具的建造上下文：让碰撞体准备和预览身份对应本次命令，明确共享状态的保存、恢复和异常清理；继续由原生 `CheckBuildConditions()` 决定合法性。若证据证明是真实建筑或矿脉占位冲突，则修正调用方位置并保留原生拒绝。
4. 修复后验证空地、有植被、重叠已有建筑、矿机覆盖矿脉四类情况，并比较不同 UI 建造状态。合法位置必须实际建成；真实重叠必须拒绝且不新增预建、不消耗建筑物品。随后才恢复生产线验收。

## 范围

不自行重写碰撞算法，不忽略 `Collide`，不关闭真实碰撞体，不把矿脉/植被统一排除，不以不断换坐标代替根因定位。此次仅处理建造流程；原型与配方查询仍由另一个任务推进。

## 联合验证结果（2026-09-24）

查询改动完成后，`items.prefabDesc.buildColliders`、`portPoses`、`slotPoses` 和 `factory.objectConnections(entityId: ...)` 已可实机读取。诊断时使用完整工作区构建；临时碰撞日志代码已移除，日志保留在本地 `.tools/blue-validation/collision-diagnostic.log`。

发现两个不同问题：

1. 原矿机位置确实与矿石碰撞。原生矿机有两个位于局部 `(±2, 0.5, -3.5)` 的支脚碰撞盒，半尺寸为 `(0.4, 1.5, 0.4)`。原存档 3 号矿脉的球形碰撞体半径为 `0.5`；换算到矿机局部坐标约为 `(-2.123809, 1.053775, -3.089535)`，到第二个盒的最近距离约 `0.010465`，两者相交。植被使用 layer 10；矿脉使用 layer 11，原生矿机对 layer 11 另做 `Physics.CheckBox`。原存档请求 `task:4` 重现 `Collide`，当时无活动 UI 工具，建筑重叠缓存为空。
2. 矿机跳过 `ActivateBuildColliders` 会漏检已有建筑。在合法矿机实体 5 旁偏移约 `0.234` 米再次下单，修复前 `task:8` 实际建成了重叠实体 8。这不是任务 ID 误匹配，实体池确认两个实体位置不同且均存在。已用 `task:9` 回收实体 8，保存为修复前回归现场。

修复只去掉矿机跳过碰撞体激活的分支，所有普通建筑都准备附近建筑碰撞体，再由原生校验决定能否建造。没有修改碰撞盒、掩码或忽略原生错误。

原位置沿北向移动 `1.2` 米仍与 3 号矿脉相交，原生拒绝；移动 `1.8` 米后最小净间隙约 `0.499` 米，`task:6` 实际建成实体 5，覆盖矿脉 `1,2,3,6,5`。另一存档中矿脉碰撞位置不同，同一旧请求曾建成实体 74，已回收；不把不同存档的成功当作原存档修复证据。

修复后 DLL SHA-256：`2C4E6A2E4CEE589904C6449F690635E76915B9FC2C5C077820C826E21252AB7E`。重启后同一重叠请求 `task:1` 返回 `collision`，实体仍只有原矿机、预建为空、库存矿机仍为 1。合法新增位置 `task:2` 建成矿机实体 8。多矿区及密集摆放验证继续记录于下文。

## 成就文件报错

退出前日志顺序为 `Auto saving to <last exit>`、存档写入完成、`GameMain.End()`、`UIRoot.OnGameEnd()`，随后原生 `AchievementSystem.SaveToFile()` 报 `IOException: Sharing violation`。涉及成就文件，不能据此断言 `.dsv` 存档失败。

Mod 的 `/game/save` 经主线程队列调用 `GameSave.SaveCurrentGame`，未直接打开成就文件。原生保存、退出和成就更新都可能调用 `AchievementSystem.SaveToFile`，其中以独占方式打开文件，并用 `using` 关闭。当前只有一个游戏进程；尚未定位产生占用的调用或外部进程，因此只确认退出操作触发了报错，不能断言 Mod 完全无关。修复版重启后的加载和初轮建造没有再次出现该错误。
